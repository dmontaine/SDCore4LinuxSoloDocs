Title: SD and AI Agents: the Guide, the Knowledge Pack and the Skill
Subtitle: What an AI agent is given to work in SD Core for Linux Solo, how it is kept true, and the two rules that do not bend: the walls are walls, and what is not a wall is not a permission.

An AI agent (Claude Code, or any tool that reads files) that is asked to write SD BASIC meets a language that looks like OpenQM, UniVerse or D3 and is not. It guesses names that SD lacks, and the compiler's answer to a missing function is a complaint about a matrix nobody declared. This page describes what the source repository holds to prevent that. **It holds documents and a generator. It does not connect an agent to SD, it holds no key, it calls no model, and nothing in it is installed on the computer by the installer.** It is the `sdb_ai/sd64/agent-pack` folder of the source tree.

## What is in it

| | |
|---|---|
| **The guide** (`guide/sd-basic-guide.md`) | about eight thousand words: the language, the system around it, and what SD does not have, with twenty-odd worked programs. Every block in it is compiled by `gplbld/sandbox-guide.py` on a private Solo, in a plain session of `sduser` that has not typed `admin`; every `run` block is run and must print what the guide says; and every line of the guide's table of missing names must still fail to compile, so that the day SD gains one the guide fails its own test. A sentence with no probe is marked `[unverified]` |
| **The knowledge pack** (`pack/`) | generated by `mkpack.py` from the sources: one chunk for each TCL verb and query keyword, VOC record type and layer, dictionary item type, format and conversion code, BASIC statement, function, `$mode` and `option`, message, `sd.conf` setting and key constant, with the file and line each came from. Real VOC records and real dictionary items are quoted verbatim. There is **no chunk for an account word**: Solo has none |
| **The skill** (`skill/sd-core-solo/`) | a Claude Code skill: `SKILL.md` and, under `references/`, the guide and the pack. An agent that is installed with it reads the guide first and looks items up by chunk id |
| **A CLAUDE.md template and the recipe** | for a project that lives in the Solo account, and for giving the agent a computer of its own. The recipe is described for the owner on the Getting Started page *Giving an AI Agent an Installation of Its Own* |

## How it is kept true

The pack is not typed. Its rosters are computed: a verb is a VOC record of type `V`, a message is a file, a statement is a name in the compiler's tables, a setting is a branch of the configuration reader. Meaning that no program can state (what a query keyword does) is quoted from this documentation by heading, and the generator **refuses to write** if a heading it needs has gone or a verb has no syntax line. The free check `gplbld/test-pack-units.py` regenerates the pack and fails if it differs from the committed one, and the check `gplbld/sandbox-pack-examples.py` reads the pack against a running Solo: every verb's type and dispatch, every shipped VOC record and every shipped dictionary item must be what the pack says, and the three refusals an agent meets first must print the words the pack gives.

A change to a verb, a message, the compiler's tables, a documentation section the pack quotes or the guide turns the check red until the pack is regenerated and the difference read:

```
python3 sdb_ai/sd64/agent-pack/mkpack.py --write
```

The line numbers in a chunk's `src=path:line#hash` are locators that may lag after an edit elsewhere in the same file; the eight-digit hash of the cited line is what is held.

## The rules that do not bend

**The walls are walls.** Solo has one account and two switches on it. What stops a session is the account password, `admin` (the administrator commands, and any change to the VOC), the `sh` and `os` switches (off as delivered: the shell, `os.execute`, a file outside the account, Python), the global catalogue (changed only by the SD Core server) and the compiler's list of names that only SD's own programs may use. The guide shows the refusal each one gives, run in a plain session that has not typed `admin`, and teaches no way round any. When one stops an agent, the instruction in the guide is to say which wall it was and to stop; whether to unlock `admin` is for the person who owns the machine, and the guide has an agent neither type, guess nor look for the password.

**What is not a wall is not a permission.** With the `sh` and `os` switches off, `sh`, `!`, `os.execute` and a path outside the account are refused (the Getting Started page *Operating System Access*); with a switch on they run with the Linux user's own rights, and the switch is the user's to turn on, not the agent's. The guide shows each refusal, says what is open when a switch is on, and tells the agent to use an open one only for what the user asked and never to ask for a switch. It also warns of one misleading message: status 3035 on a write to the VOC is the `admin` wall, whatever the run-time text says about a full disk.

## What it does not do

It does not make an agent right; it makes the commonest mistakes cheap to avoid. It has not been measured with a model (the plan has a benchmark of thirty tasks, run with and without the guide, and it is not built). It describes SD Core for Linux Solo at its stamp plus what has been carried into it from the full product's release in progress; items marked 1.2-0 may be missing from a released install. SD Core for Linux has its own pack, made from its own sources, and the two differ where the products do: `agent-pack/README.md` lists every difference and why.
