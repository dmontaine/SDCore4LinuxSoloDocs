# SD Core for Linux Solo — documentation

Documentation for **SD Core for Linux Solo LS1.1-3**, a personal SD Core for one
Linux user. The source is in a separate repository, `SDCore4LinuxSolo`; nothing
here is needed to build SD, and nothing there is needed to build these pages.

**Written 30 Sep 2026 from `SDCore4LinuxDocs` (the multiuser SD Core for Linux
L1.1-1) and `SDCore4WindowsSoloDocs`, and checked against a staged Solo tree.**
The GettingStarted set is a full rewrite; the User set (SD BASIC, TCL, the VOC)
is the multiuser one with the account, path and gate statements corrected for
Solo and its syntax cards regenerated from the Solo VOC and compiler. Where a
page says something was *not measured* on Solo, that is the record: the list is
GettingStarted `19`.

**This repository does not have the server repository's no-binaries rule**, and
it does not track the rendered pages anyway — see *Generated* below.

## Layout

Two document sets, each with the same three folders:

| | |
|---|---|
| `GettingStarted/` | **28 pages** — installing, upgrading and uninstalling SD Core for Linux Solo, running it, the one account and its three passwords, the administrator commands, sessions and locks, operating system access, ssh and the API, security, managed mode, configuration, limits, the installed scripts, encryption, and what nobody has tested. `01b` is *Differences from multiuser SD Core for Linux L1.1-1*. The multiuser product's Administrator set is merged in here |
| `User/` | **two references.** `01`-`18` SD BASIC by subject, where `18` is Modern Program Structure. `19`-`31` SD TCL by subject. `32`-`34` VOC and dictionaries. `35`-`40` file system, standard subroutines, client API, glossary, terminfo, and a tutorial with worked programs, and `37a` embedded Python. **The generated cards live at the end, `94` onwards**, so more can be added without renumbering anything: `94` SD BASIC (372 names an application may use), `95` SD TCL (143 verbs), `96` the 76 names an ordinary program may not compile |

Inside each: `markdown/` is the source, `html/` and `pdf/` are generated.

### A number with a letter after it is the second half of a long page

**No page runs longer than about 14,000 characters of Markdown** (owner, 5 Sep
2026). **The first half keeps the number and the second takes a letter** — `06`
and `06a`. Every link and every map entry written to `06` still lands on `06`.
`06-` sorts before `06a-` and both before `07-`, so directory order is reading
order. The one exception is `94`, the SD BASIC syntax card: a lookup table read
with Ctrl-F, kept whole.

**`00a` and `00b` are order, not halves.** `00a-copyright-and-licence` and
`00b-start-here` (`00b-sd-introduction` in the User set) put the licence page
first: `00-` would sort before `00a-` and open a set with the introduction.

### The copyright and the licence appear once per set

The licence block comes off every page and is stated once per set, on `00a`; every
page carries a footer tag line with the product, version, copyright and licence
name. **The words are generated by `mkdoc.py`**: a page asks for the block with a
`<!--LICENCE-BLOCK-->` marker in its Markdown. `add_nav.py` refuses a set that has
anything other than exactly one page carrying it, or whose licence page is not
first, and `mkbook.py` refuses a book whose first document is not the licence page.

**Sets never link to each other.** Each set is handed out on its own, so a link
from one to another would be a 404 for whoever was given only the first. Where a
page in the other set is worth naming, **name it in words**. `checklinks.py`
checks every link that does exist.

## Building

Every step is a plain Python script; the only dependency is **python-markdown**
(`pip install markdown`, or your distribution's `python3-markdown`).

```
python3 tools/mkdoc.py --in GettingStarted/markdown --out GettingStarted/html
python3 tools/mkdoc.py --in User/markdown --out User/html
python3 tools/add_nav.py
python3 tools/checklinks.py GettingStarted/markdown GettingStarted/html
python3 tools/checklinks.py User/markdown User/html
```

`start-docs.sh` serves the rendered tree at `http://localhost:8123`.
`tools/mkpdf.sh` renders a PDF with headless Chrome or Chromium, and
`tools/mkbook.py` / `mkbookpdf.py` bind a set into one document. `tools/rebuild_html.py`
is an older renderer kept for reference; use `mkdoc.py`.

## Regenerating the syntax cards

**The cards are generated, not edited.** From the repository root, with the Solo
source tree at `SDCore4LinuxSolo`:

```
SD64=/path/to/SDCore4LinuxSolo/sdb_ai/sd64
python3 tools/mksyntax.py    $SD64/sdsys/gpl.bp/bcomp User/markdown/94-sd-basic-syntax.md User/markdown/96-sd-basic-restricted-commands.md
python3 tools/mktclsyntax.py $SD64/sdsys               User/markdown/95-sd-tcl-syntax.md
```

`mksyntax.py` reads the compiler's own tables and **refuses to write the pages if
any name accepted by the compiler has no line** — 448 of 448, split 372/76 between
`94` and `96`. Everything a count cannot express lives in `tools/syntax-shapes.txt`,
one `NAME = syntax` per line. `mktclsyntax.py` computes its roster from `newvoc`
(143 verbs) and refuses if a verb has no line in `tools/tcl-syntax-shapes.txt` or a
line names something that is not a verb.

## Checking a set

```
python3 tools/docmap.py   $SD64/sdsys/gpl.bp/bcomp   # every compiler name is on exactly one User page
python3 tools/tclmap.py   $SD64/sdsys/newvoc         # every TCL verb is on exactly one page, evidenced
python3 tools/confmap.py  $SD64                      # every sd.conf parameter is documented once
python3 tools/verbcounts.py $SD64/sdsys/newvoc       # every verb count in prose against the VOC
python3 tools/linkup.py   User/markdown              # *SD Basic - X* becomes a link only for pages that exist
```

| | |
|---|---|
| `docmap.py` | assigns every name the SD BASIC compiler accepts to exactly one document. **448 of 448** |
| `tclmap.py` | the same for the TCL verbs, across both sets — **and it checks the page actually documents the verb**, not merely that the name occurs. **143 of 143** |
| `confmap.py` | the same for the parameters `config.c` accepts, and it reports which of them anything still reads |
| `verbcounts.py` | every verb count written in prose, against the counts computed from the VOC (143) |
| `linkup.py`, `checklinks.py` | turn a named page into a link only if it exists; check every link in the rendered pages, anchors included |

`scriptmap.py`, `sdcompile.ps1` and the other `.ps1` files are the Windows
repository's and are kept only so that the two repositories' `tools/` stay
comparable; **nothing in them has been run for Solo.**

## Generated, not tracked

`*.html`, `*.pdf` and `*.zip` are ignored. The deliverables are built from the
Markdown at release time, so tracking a rendered copy would only add a way for the
two to disagree.
